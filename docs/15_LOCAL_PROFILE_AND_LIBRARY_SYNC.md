# T060 — локальний профіль і синхронізація Library

**Статус.** Проєкт для наступної реалізації. Поточна Library працює в Room v2 і зберігає статус, необов’язкову оцінку, загальний ручний лічильник та ID зарахованих епізодів. Нижче визначено, як зберегти цю поведінку при роботі з кількох пристроїв. · [Обсяг v0.5.0](01_SCOPE_AND_RELEASES.md).

## Профіль і межі даних

- **Гість.** При першому запуску VIRA створює постійний локальний `profileId`. Гість може додавати й видаляти тайтли, змінювати статус, оцінку й прогрес без акаунта та мережі. Записи гостя залишаються на цьому пристрої до явного імпорту.
- **Акаунт.** Після входу окремий локальний профіль прив’язується до стабільного `accountId`, підтвердженого сервером. На пристрої активний один профіль. Відкриття Library, картки й запис із плеєра отримують ідентифікатор профілю. Ключі локальних рядків, завершених епізодів, черги, конфліктів і курсорів містять `profileId`.
- **Втрата мережі.** Профіль, який був активний до втрати зв’язку, продовжує працювати з Room. Якщо потрібен повторний вхід, застосунок показує стан **Потрібен вхід для синхронізації** й тримає зміни в черзі цього профілю.
- **Вихід або зміна акаунта.** Припиняється синхронізація попереднього профілю, очищаються його токени та видимі дані у Library й картці. Черга попереднього акаунта лишається у приватному сховищі застосунку до повторного входу в той самий акаунт. Пізні відповіді та завершення відтворення від попередньої сесії відкидаються. Гість і новий акаунт відкривають тільки власні записи.

Синхронізуються статуси, оцінки, ручні зміни лічильника, ID завершених епізодів і видалення тайтлів. Позиція відтворення, просторовий стан Anime Card, відео й доступи до провайдерів мають окремі життєві цикли. Стабільні ID тайтлів та епізодів мають власний простір імен джерела. [Межі компонентів](05_TECHNICAL_BASELINE.md) · [Безпека](14_SECURITY_AND_RIGHTS.md).

Сервер визначає власника за перевіреною сесією і перевіряє доступ для кожної операції та вибірки. Клієнтський `profileId` служить для локальної ізоляції. Клієнт перевіряє профіль і покоління сесії перед застосуванням відповіді або записом прогресу з плеєра. Токени зберігаються окремо від Room у захищеному сховищі Android. Провайдер входу й серверне сховище обираються на етапі реалізації. Якщо оберемо OAuth для входу, нативний клієнт використовуватиме системний браузер і Authorization Code з PKCE. [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html).

## Офлайн-робота й повернення мережі

1. **Локальна транзакція.** UI читає видимий стан із Room. Дія одразу оновлює цей стан. Для акаунта та сама транзакція додає операцію в постійну чергу. Після перезапуску видимий стан і черга доступні знову. [Android offline-first](https://developer.android.com/topic/architecture/data-layer/offline-first).
2. **Завантаження змін.** Коли мережа й сесія доступні, клієнт отримує зміни після курсора акаунта. Підтверджений стан, курсор і видимий стан з урахуванням локальної черги оновлюються разом у Room. Черга зберігає версії, на яких користувач зробив зміни.
3. **Відправлення.** Кожна операція містить `opId`, тип, аргументи, ID тайтлу, покоління його запису та потрібну версію поля. Сервер атомарно зберігає результат і, коли дані змінилися, запис та подію синхронізації з `opId`. Повтор після втрати відповіді надсилає той самий `opId` і ті самі аргументи та отримує той самий результат. Повторне використання ID з іншими аргументами відхиляється.
4. **Підтвердження.** Отримання власної події знімає локальну операцію в тій самій транзакції, що застосовує підтверджену зміну, навіть якщо відповідь на запис загубилася. Для операції без зміни або відновлення зі знімка клієнт звіряє результат за `opId` і знімає операцію, коли завантажена послідовність досягла серверної версії з підтвердження. Пізніша зміна могла вже замінити значення. Курсор рухається лише після послідовного завантаження.
5. **Повтор і помилки.** Тимчасова помилка залишає операцію в черзі з поступовою затримкою між спробами. Конфлікт поля зберігає локальний варіант для вибору. Помилка доступу призупиняє відправлення до повторного входу. Застарілий курсор запускає завантаження узгодженого знімка. Непідтверджені операції зберігаються й перевіряються за початковими версіями.

Для одного поля на пристрої наступна зміна чекає на результат попередньої. Якщо попередню прийнято, наступна використовує версію з її відповіді. Якщо виник конфлікт, VIRA зберігає намір пристрою й пропонує вирішити його разом із залежними локальними змінами. Зміни інших полів можуть синхронізуватися паралельно.

Для користувача достатньо чотирьох станів **Збережено на пристрої**, **Очікує синхронізації**, **Синхронізовано** й **Потрібен вибір**. Гість завжди бачить локальний стан. Серверний статус синхронізації з’являється лише для акаунта.

## Правила конфліктів

Сервер присвоює версії й порядок прийнятим операціям. Для статусу, оцінки та ручного редагування прогресу використовуються окремі версії. Це дозволяє об’єднати зміни різних полів і виявити дві незалежні зміни одного поля. Порядок визначається на сервері без прив’язки до годинника шолома.

| Поле | Як об’єднуємо |
|---|---|
| **Статус** | Явна зміна на Planning, Watching або Completed. Якщо версія збігається, застосовуємо вибір. Якщо інший пристрій уже записав відмінне значення, зберігаємо підтверджене й показуємо обидва варіанти. |
| **Оцінка** | Окрема зміна цілого бала 1–10 або очищення через `null`. Застосовуємо ті самі правила версій, що й для статусу. Операція без поля оцінки його не змінює. |
| **Завершена серія** | За кожною парою «покоління тайтлу, ID епізоду» сервер зберігає один факт. Новий факт і збільшення лічильника записуються однією транзакцією. Два пристрої, що завершили одну серію, додають разом одну одиницю. Різні серії дають по одиниці. Вхідна команда формується за правилом повного перегляду з T052. |
| **Ручний прогрес** | Кнопки `+` і `−` передають зміну на одну одиницю. Якщо версія ручного редагування збігається, сервер застосовує зміну до поточного лічильника з межами 0…2 147 483 647. Автоматичне зарахування серії цієї версії не змінює. Якщо два пристрої редагували вручну з однієї версії, другий отримує вибір між поточним числом і повторним застосуванням свого коригування. |

Для статусу й оцінки однакові значення узгоджуються без запиту. Після конфлікту Library показує підтверджене значення та позначку **Потрібен вибір**. Користувач може залишити його або застосувати свій варіант як нову операцію на поточній версії. Для кількох ручних коригувань показуємо число, яке утвориться після застосування збережених кроків у порядку вводу. Так мінус враховується й після нової завершеної серії, а повторне надсилання не додає той самий крок удруге.

**Приклад.** Обидва пристрої бачать прогрес 8, а E1 уже зарахована. Офлайн A завершує E2, натискає `−1` і очищає оцінку. B теж завершує E2, потім E3, і змінює статус на Completed. Після синхронізації прогрес дорівнює **9**, оцінка порожня, статус **Completed**, а E2 зарахована один раз. Якщо B водночас поставить оцінку 7, для оцінки з’явиться вибір між **7** і **без оцінки**.

## Додавання й видалення

Кожне створення запису має нове покоління. Видалення закриває поточне покоління, а сервер зберігає позначку видалення. Запізніла операція для цього покоління відхиляється. Явне повторне додавання після синхронізації створює нове покоління. Після одночасних перших додавань другий пристрій бачить уже створений запис. Залежні локальні зміни потребують узгодження, якщо їх створено для іншого покоління.

Перша повна серія незбереженого тайтлу може створити запис **Watching**, коли клієнт працює з актуальним поколінням відсутності тайтлу. Це дозволяє зарахувати перший перегляд і захищає від повторного створення запису за давньою офлайн-операцією. Сервер зберігає версію видалення й можливість впізнати повтори до впровадження окремої політики очищення історії.

## Перехід із Room v2 та імпорт у акаунт

При міграції всі наявні записи стають Library локального гостя. Копіюємо точні статуси, оцінки, лічильники й наявні ID завершених серій. ID виступають історією вже зарахованих серій, тому перенесення саме по собі не додає прогресу. Старі ручні числа не мають відомих ID епізодів. Доступ до старих даних зберігається в разі відмови від імпорту.

Імпорт до акаунта починається тільки після підтвердження. Для тайтлів, яких ще не було в акаунті, переносимо значення й відомі ID цілком. Якщо запис видалено, його повторне створення підтверджується окремо. Для дублікатів користувач обирає статус, оцінку й базовий лічильник. Після підтвердження об’єднуємо відомі ID. До вибраного лічильника додаємо лише ID, яких не було в його історії, і застосовуємо межі. Очищення оцінки акаунта потребує явного вибору. Якщо серверні дані змінилися після попереднього перегляду імпорту, клієнт повторно показує результат для підтвердження. Повтор імпорту після втрати відповіді використовує той самий ідентифікатор.

## Сценарії приймання для реалізації

| Сценарій | Очікуваний результат |
|---|---|
| Гість без мережі додає тайтл, змінює статус, оцінку та прогрес, перезапускає VIRA | Усі локальні значення відновлено. Гостьові дані не надсилаються. |
| Room v2 переносить статус, оцінку 7, прогрес 8 та відомі ID епізодів | Перший і другий запуск показують ті самі значення. Відомі серії лишаються вже зарахованими. |
| Офлайн-зміна акаунта A, вихід, вхід в B і пізня відповідь для A | B і гість бачать лише власні дані. Повернення в A відновлює чергу A. Пізній результат старої сесії не може змінити B. |
| Сервер записав операцію, а відповідь втрачена | Повтор повертає попередній результат. Лічильник і запис змінюються один раз. Курсор не пропускає інших подій. |
| A очищає оцінку, B змінює статус | Обидві зміни застосовано. Дві різні оцінки з однієї версії переходять у видимий конфлікт. |
| Два пристрої завершують ту саму серію, а один завершує ще одну | Додаються дві одиниці загалом. Ручне `−1` з актуальною версією дає на одиницю менше. |
| Два ручні коригування однієї версії біля нуля або максимуму | Прийнятий крок застосовується в серверному порядку з межами. Другий потребує вибору. |
| Видалення, повторне додавання, пізня операція старого покоління | Операція відхиляється. Стан нового запису лишається коректним. |
| Однаковий тайтл у гостя й акаунті | До підтвердження записи окремі. Під час імпорту користувач бачить попередній результат, а повтор команди не дублює записи. |

Перший етап реалізації охоплює міграцію, локальні профілі й чергу з тестовим сервером. Другий перевіряє протокол на реальному сервері з двома ізольованими акаунтами. Перевірки синхронізації та входу для T060 мають статус `NOT_RUN`.
